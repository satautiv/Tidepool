# Tidepool playtest round 1: AI tester sessions

Sep 27, 2026 · @Vytautas

## Summary

Two AI testers each played about 20 minutes on desktop Chrome. Both picked up the game in about 30 seconds without help, rated it 4/5 for fun and 4/5 for calm, and blamed themselves for their losses. The main problems they found are readability: nothing explains column clears or the combo multiplier, and a rejected drop gives no feedback. The game also looks too easy. In 118 logged moves the board never passed 60% full, and every clear was a single line.

- **Magnet assist:** no decision. AI testers drop with pixel precision, and invalid drops were 2 in 111 moves with magnet off versus 1 in 109 with it on. This needs human testers.
- **4-cell L/J:** leave off for now. Neither tester called the pieces repetitive.
- **Generator weights:** no one answered "unfair", so the rule doesn't trigger a retune. Both testers said the early game was too easy, though, so it's worth a look.
- **Animation timing:** no change. No one called anything slow or twitchy. Testers only see before and after screenshots, so they can't judge this.
- **Resume and settings:** worked for tester-2. Tester-1's session was broken by a second Tidepool tab overwriting storage.

Artifacts: `tester-2.json` (the full log). Tester-1's log was lost; the key numbers were captured before it was overwritten.

## Setup

Both sessions used build `6356ce4` on [GitHub Pages](https://satautiv.github.io/Tidepool/) in desktop Chrome (1162×895 viewport, Windows) with playtest mode on. They followed the [round 1 plan](https://github.com/satautiv/Tidepool/blob/main/docs/playtests/round1-plan.md).

| Tester | Variant order | L4 run | Fresh save |
| --- | --- | --- | --- |
| tester-2 | magnet off → on | no | yes (progress reset first) |
| tester-1 | magnet on → off | no | no (1 piece already placed) |

- **Tester:** a separate AI agent with no information about the game. It could only use screenshots, mouse and keyboard. It had no page source, storage or repo access, and it wasn't told the variant difference.
- **Observer:** Claude. It set the variants with the URL parameters, read the playtest log from browser storage, and asked the questionnaire.
- **Timing:** the plan's minutes were replaced with move caps (40–70 moves per part), because an AI plays slower per move but never tires.
- **Caveats:**
  - The tester sees only still frames before and after each drag, so it can't judge drag feel, animation or sound.
  - Its drops are pixel-precise, which makes the magnet comparison meaningless.
  - It knows the Block Blast genre, so "understood without help" overstates what a non-gamer would manage.
- **Plan mismatch:** `?playtest=1` didn't reset magnet to on. The saved `magnet:false` from an earlier visit stayed, so `?magnet=1` was needed.

Tester-2 was the clean session: fresh save, magnet off then on, full log kept. Profile: desktop Chrome, knows block puzzles.

- Hint hand noticed: **no, none appeared.** The first move came within seconds, so a hint triggered by idle time may never have fired.
- Time to first clear: move 5, 38 s after the page loaded. The log says `playMs 55904`, which is inflated (see Bugs).

- Confusion: the combo multiplier (colours and values change with no explanation; it once rose on a move with no clear); no tutorial at all.

## Bugs and issues

The most serious issue is data loss with two tabs open. The rest are logging gaps and small UX fixes, each a candidate follow-up issue.

| # | Issue | Seen by | Severity |
| --- | --- | --- | --- |
| 1 | Two open Tidepool tabs overwrite each other's `tidepool.save` and `tidepool.playtestLog` (last writer wins). This wiped tester-1's run, settings and log. | observer | High |
| 2 | No `run_start` is logged for a run begun with **Play**; it's only logged after **Play again**. | observer (both logs) | Medium |
| 3 | `first_clear.playMs` is inflated for the first run (55.9 s logged vs 38 s real; 433 s for tester-1). It seems to count time from before the run started. Correct for later runs. | observer | Medium |
| 4 | `run_end` is only written when the player leaves the end screen, so closing the tab on "Out of room" probably loses the run record (not tested). | observer | Medium |
| 5 | `?playtest=1` doesn't reset magnet to on as the plan says; a stored `magnet:false` survives. | observer | Low (docs or code) |
| 6 | No hint hand or tutorial appeared for a fresh player. | both | Medium |
| 7 | A rejected drop gives no feedback (no shake, flash or sound). | both | Medium |
| 8 | Column clears and the combo multiplier are never explained. | both | Medium |
| 9 | During the score count-up, Best shows the final value while Score is still counting. | both | Low |
| 10 | Title and Settings panels are centred on the window, not the board, so they overlap the board's right half. | both, observer | Low |
| 11 | No warning when no tray piece can fit; game over is instant. | both | Low |
| 12 | Pale sand and lavender pieces read as disabled. | tester-1 | Low |
| 13 | Pause isn't restored on resume; the Music slider greys out only after a reload. | tester-2 | Low |

## Decisions

These are provisional. Two AI testers can't settle anything that depends on human hands or ears, so the plan's human round still needs to happen.

| Question | Rule from plan | Result | Suggested decision |
| --- | --- | --- | --- |
| Magnet assist | Keep if invalid drops fall noticeably with it on, and testers prefer it or don't notice | Invalid drops: 2 in 111 moves off, 1 in 109 on. Neither tester noticed a difference. | Keep on (the default) until human data exists |
| 4-cell L/J | Turn on if pieces are called repetitive and `npm run sim` stays healthy | Called "varied enough"; one tester found the early game repetitive because of small pieces | Leave off |
| Generator weights | Retune if most answer "unfair" to Q3 | 2 of 2 "my fault". Board never above 60% full in 118 moves; no multi-line clear was logged. | No retune required; consider fewer singles and dominoes early, checked in `npm run sim` |
| Animation timing | Change `feel.ts` values called slow or twitchy by more than one tester | None called slow or twitchy (can't be judged from screenshots) | No change |

Next: fix bugs 1–4 before human sessions so their logs are trustworthy, and open follow-up issues for the rest.
